# UI-only mock data specification

Planning baseline: official DeepTutor v1.7.1, commit `f7aed0744c36c5afef16a4261c31ebee1208cac2`. Audit inputs: [135 surfaces](audit/screen-inventory.md), [63 page files](audit/route-map.md), [design](audit/design-system.md), [captures](audit/screenshot-catalog.md), [validation](audit/validation.md). Existing audit files and all application code remain unchanged.

**VERIFIED** = source-confirmed behavior, or an explicitly scoped observed capture. **UNVERIFIED** = runtime/presentation not established. **PROPOSED** = every mobile destination, component arrangement, fixture and acceptance contract below. Source verification never establishes that an asynchronous backend operation succeeded. Synthetic fixture content is allowed for UI development; it is not a new product capability or an API contract.

## Boundary and implementation contract — PROPOSED

Future UI work uses deterministic in-process fixture repositories/view-state drivers under `src/features/<owner>/fixtures` and `src/shared/fixtures`, never HTTP interception or a fake remote backend. This phase creates no fixture code and makes no API change. Listed fields are presentation projections, not invented server JSON schemas; when later integration starts, derive types from the audited contract owner and map them to the existing view projection.

Use two independent axes: resource state (`loading`, `ready`, `empty`, `error`, `denied`, `unavailable`) and operation state (`idle`, `busy`, `success`, `failure`, plus feature-specific stages). An empty ready list must not hide an error. Pending auth/module/catalog decisions must not expose unauthorized actions. `success` means a local fixture transition only, never completion of an external operation.

Scenario IDs are stable `<surface ID>.<state or variant>`, for example S05.stream-disconnected, S25.conflict, S63.revision-conflict and S42.index-failed. Each S01–S135 must have a ready scenario; backend/data surfaces must also have loading/empty/error and applicable denied/unavailable/operation-failure scenarios. For purely local controls use closed/idle/invalid/busy equivalents instead of inventing network states. Scenario selection is a development/test harness, not an invented learner settings page.

Keep fixtures in memory for the UI session by default. Reset via the developer harness, not a product Reset data feature. Presentation preferences may later use the existing AsyncStorage dependency, but mock conversation/accounts/credentials must not be silently persisted. All fixture clocks, delays, IDs and random values are deterministic. Default wait 400 ms; long-loading scenario remains pending until the harness advances it. Script stream/ingestion events through an injectable clock; advancing twice must not duplicate a message, question rating, save or import.

No live `src/api/client.ts` import is allowed in the fixture dependency graph: it throws when EXPO_PUBLIC_API_URL is absent. UI previews must run without that variable and without a network connection. No real credentials, channel QR codes, OAuth callbacks, server folders, provider tests, model calls, index jobs or notifications are initiated. Simulated outcomes retain a development/demo indicator, not new source product copy. Do not put fixture implementation details into normal learner flows.

## Fixture graph and data integrity

- Synthetic principals: `fixture-admin`, `fixture-standard`, `fixture-learner`, auth-disabled and auth-unavailable. Preserve audited preset/grant meanings; fixture role changes are never server authorization.
- Content workspaces: `fixture-ws-a` and `fixture-ws-b`, plus audited general/system scope examples where applicable. Account-owned Partners/Personalization are not duplicated on workspace switch. Calendar items use the actual source scope projection rather than forcing the same workspace cache pattern.
- Connected chain: session-a → turn-a/message-a → typed source refs; path-a → module/point → study-session-a; book-a → page-a → block-a; collection-a → material-a/unit/locator → reading-session-a. Keep Reading collection ID independent of content workspace ID.
- Original Favorites record-a points back to its source; editable note-a/block-a can cite it but does not replace it. Question-a carries source reference/contentWorkspaceId; Practice run-a records ratings by entry reference; note flashcard-a retains page/block/card IDs and a separate remembered/not review result.
- KB-a owns file-a/source-a/index-run-a/index-version-a; only read-only/provider-eligible fixture sections appear. Engine-a is not a KB-a ID. Memory resolver refs point to existing layer/surface/line records.
- Partner-a owns session-a under account scope and may bind a content workspace; group-a uses actual member IDs and attributed rounds. Live agent connection-a and imported-history agent-a are different record kinds.
- Settings holds active + staged + saved-draft values separately. Apply failure does not overwrite active configuration; Discard clears pending changes consistently across pages. Admin CSV import outcomes reference synthetic user IDs, preserving per-row errors.
- Display content may use a small synthetic mathematics topic and neutral study text, clearly tagged as fixture. Do not copy a real learner transcript or claim source screenshots supplied populated content. Include short/long titles, Unicode/10 locales, multiline errors, zero/one/many rows, large message/file/question lists and read-only examples.
- Dates use a fixed clock and explicit timezone. Calendar covers all-day, timed, recurring exception and daylight-transition examples supported by the source model. No fixture invents a new recurrence or grading algorithm.

## Required exceptional scripts

- Chat: first-send identity binding; partial stream then disconnect/resume without duplication; cancel pending/accepted/failed; structured reply submit failure; unknown protocol; edit/retry/discard failure; copy and playback failure; invalid attachment. Fixed final response is never labeled live AI.
- Learning: hidden versus unavailable surfaces; Mastery Outline→Study→Review with busy mode lock; objective/board error; reset versus permanent delete; Practice conflict reload/Again queue/skip/completion; Bank no-match and empty Mistakes.
- Books/Reading: proposal rejection/edit/confirmation; unhydrated page; generation paused/failed; missing/corrupt file; EPUB reflow and PDF page anchors; annotation save failure; media unavailable provider; source note organization failure. Use bundled media/HTML/SVG/docs only when their source renderer type is supported; otherwise show explicit preview unavailable rather than fake content.
- Knowledge/integrations: read-only KB; engine-specific fields; probe failed; queued/running/failed/ready index; failed retry; no versions; account versus deployment MCP; installed/granted/enabled CLI; server folder permission denial; import mixed success. Progress is scripted at a UI boundary, not a fabricated live task.
- Notes: loading, dirty, saved, expected-revision conflict with recoverable draft, failed source import, accepting/rejecting a fixed suggestion, due flashcard reveal/remembered/not/empty, sample export. Native/web editor fidelity requires renderer spike evidence beyond mock state wiring.
- Partner: five-step validation, missing/backup model, continuity resolving/error/retry, invalid session prevents silent new-session fallback, channel QR waiting/expired/connected, group round attribution and mode/member changes. Never scan/connect an external channel from fixtures.
- Settings/admin: pending/unavailable access, admin/learner/guardian field visibility, clean→unsaved→saved-draft→applied, failed apply and discard, mocked discovery/test/OAuth states, network restart-needed only if source owner reports it, mixed-row CSV and bulk confirmation failure. No source account/grant/storage migration is executed.
- Handoff: blank input, invalid/expired/already-used code, unsafe return path and local accepted state. Existing captures failed for /handoff, so its visual layout follows source until a new real capture is available.

## Fixture acceptance gate

Every screen contract in IMPLEMENTATION_PLAN must be exercisable from direct entry in each required fixture state and from its normal owner action. Error Retry advances only the requested fixture; Close/Back preserves owner identity and unsaved input according to source semantics. UI-only tests assert navigation, visible state, interaction eligibility and local transition, not correctness of unimplemented backend algorithms or services. Before live integration, remove no fixtures until equivalent source-backed successful/error behavior has been demonstrated against an isolated authorized backend.
